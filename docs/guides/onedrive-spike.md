# OneDrive Personal feasibility spike (TD-005)

This guide runs the TD-005 proof of concept: it proves (or disproves) that the
intended Microsoft Personal account can safely support the TaxDesk document
workflow before Epic 4 depends on it.

The spike is a **throwaway harness**, not the product integration. It is not
deployed, adds no Worker route, stores no token, and is not imported by the API
or the web application. The production `DocumentStorageProvider` adapter is
built in Epic 4 and is only allowed to start once this spike passes.

Everything below runs against a **non-production Microsoft application** with
**synthetic, non-confidential test files** generated by the harness. Never use
client documents, real CNIC/NTN images, or production credentials.

## What the harness proves

| Scenario | What it proves |
| --- | --- |
| `consent` | Delegated consent completes through the registered callback, grants exactly the app-folder scope plus offline access, and the application folder resolves. |
| `token_refresh` | A refresh token can mint a new access token, and the observed lifetime is recorded. |
| `upload` | A small file uploads in one request and a multi-chunk file uploads through an upload session, with byte counts verified. |
| `download` | Downloaded bytes match the uploaded SHA-256 checksums. |
| `upload_interruption` | An upload session that is dropped after the first chunk resumes from the byte range the provider reports and still stores the original content. |
| `revoked_consent` | After consent is revoked, a refresh is rejected as reconnect-required and a fresh authorization-code consent restores access. |

The harness writes a strict evidence record; any failure raises a blocking
decision (see [Outcome and blocking decision](#outcome-and-blocking-decision)).

## Step 1 — Register the non-production Microsoft application

1. Open the [Microsoft Entra admin center](https://entra.microsoft.com) →
   **App registrations** → **New registration**.
2. Name it `TaxDesk OneDrive Spike (non-production)`.
3. **Supported account types:** *Personal Microsoft accounts only*. This makes
   the token authority the `consumers` tenant, which is what a firm's Personal
   OneDrive account uses.
4. **Redirect URI:** platform *Mobile and desktop applications*, value
   `http://localhost:8788/oauth/callback`. Microsoft only permits `http` for
   loopback redirects; do not register a wildcard or an internet-facing URL.
5. Register, then copy the **Application (client) ID**.
6. **Do not create a client secret.** The spike is a public client using
   authorization code + PKCE (S256).
7. **API permissions** → **Add a permission** → **Microsoft Graph** →
   **Delegated permissions** → add only:
   - `Files.ReadWrite.AppFolder`
   - `offline_access`

   Then **Grant admin consent** if your account requires it (a Personal account
   usually consents interactively on first sign-in).

If you change `--host` or `--port`, the registered redirect URI must match the
value you pass exactly, for example `http://localhost:9000/oauth/callback`.

## Step 2 — Run the spike

From the repository root:

```bash
pnpm spike:onedrive --client-id <application-client-id> --operator "<your name>"
```

Optional environment variables:

| Variable | Purpose |
| --- | --- |
| `TAXDESK_MS_GRAPH_CLIENT_ID` | Application (client) ID, instead of `--client-id`. |
| `TAXDESK_SPIKE_OPERATOR` | Name recorded in the evidence file, instead of `--operator`. |

The command builds the harness, prints an authorization URL, and waits on
`http://localhost:8788/oauth/callback`. Open the URL, sign in with the intended
Personal account, and approve the request. Then follow the prompt in Step 3.

Progress and results are printed to the terminal. The evidence file is written
to `<repo>/docs/product/evidence/td-005-onedrive-spike-report.json` by default
(the CLI prints the absolute path; it is anchored at the repository root even
when the command runs from the package directory); use `--report <path>` to
change it.

Exit codes: `0` means every required scenario passed, `1` means the outcome is
`failed` or `incomplete` (including an aborted consent flow).

## Step 3 — Revoke consent during the run

The revoked-consent scenario is last, because it invalidates the grant. When the
harness prompts:

1. Open <https://account.live.com/consent/Manage>.
2. Remove TaxDesk's access to the test account.
3. Return to the terminal and press Enter.

The harness then attempts a refresh (expecting a reconnect-required rejection)
and performs a fresh authorization-code consent to prove the reconnect
procedure. Typing `skip` (or passing `--skip-revocation-check`) records the
scenario as `skipped`, which leaves the outcome `incomplete` and keeps the
blocking decision raised.

## Step 4 — Record the result

1. Commit the evidence file:
   `docs/product/evidence/td-005-onedrive-spike-report.json`.
2. Copy the observed values into
   [`docs/product/sprint-1-review-notes.md`](../product/sprint-1-review-notes.md)
   (scopes, callback URL, expiry behavior, file-size behavior, interruption
   behavior, reconnect procedure).
3. Update [`docs/product/status.md`](../product/status.md).
4. Only when the outcome is `passed` may Epic 4 document storage start.

## Requested permissions and why they are the minimum

| Scope | Type | Why it is requested |
| --- | --- | --- |
| `Files.ReadWrite.AppFolder` | Delegated Graph permission | The narrowest documented permission that allows creating, reading, updating, and deleting files in the application's own OneDrive folder. Everything the document workflow needs lives there. |
| `offline_access` | OAuth scope | Required to receive a refresh token; without it the spike cannot observe token refresh or revoked consent. |

Deliberately **not** requested: `Files.ReadWrite`, `Files.ReadWrite.All`,
`Files.Read.All`, `Sites.*`, `User.Read`, `openid`, `profile`, `email`, and any
application (app-only) permission. The spike records the drive it operates on
rather than the person consenting, so it does not need identity scopes.

The harness asserts this: `packages/shared/src/onedrive-spike.test.ts` fails if
the scope list grows beyond the two documented scopes, and
`packages/onedrive-spike/src/graph/oauth.test.ts` asserts the authorize URL
carries exactly `offline_access Files.ReadWrite.AppFolder`.

## Behaviour the harness records

### Two provider behaviours that surprised the first run

**`/me/drive` is out of scope.** With only `Files.ReadWrite.AppFolder`, Graph
answers `403 accessDenied` for `GET /me/drive`. The scope reaches
`/me/drive/special/approot` and its children, nothing else. The consent scenario
probes the app folder, not the drive, and records `appRoot.resolved`,
`appRoot.childCount`, `consent.requestedScopeCount`,
`consent.grantedScopeCount`, and `consent.refreshTokenIssued`.

**The app folder is provisioned lazily.** The first write to
`/me/drive/special/approot:/<name>:/content` can fail with `404 itemNotFound`
while OneDrive creates the folder. The same request succeeds seconds later. The
harness resolves the app root during the consent scenario and additionally
retries the first write of each upload path once after 1 500 ms, recording
`upload.simpleUploadRetries`, `upload.sessionRetries`, and
`interruption.sessionRetries`. A non-zero retry count is an observation, not a
failure.

**`offline_access` is not echoed.** The token response reports
`scope: "Files.ReadWrite.AppFolder"` even though a refresh token is issued. The
harness therefore proves offline access from the refresh token's presence and
records it as `consent.refreshTokenIssued`. Do not treat the absent scope string
as a missing permission.

### Token expiry

The `token_refresh` scenario records `token.initialAccessTokenExpiresInSeconds`,
`token.refreshedAccessTokenExpiresInSeconds`, and
`token.refreshTokenRotated`.

Documented baseline to compare against: Microsoft access tokens are short-lived
(typically `expires_in` ≈ 3600 seconds) and Personal-account refresh tokens are
single-use, so a refresh normally returns a new refresh token with a sliding
validity window. Record what you actually observe; do not assume the baseline.

### File-size behaviour

The `upload` scenario records `upload.simpleUploadBytes`,
`upload.simpleUploadLimitBytes`, `upload.simpleUploadRetries`,
`upload.chunkedUploadBytes`, `upload.chunkSizeBytes`, `upload.chunkCount`, and
`upload.sessionRetries`.

The harness uploads 1 MiB with a single `PUT …/content` request and 5 MiB
through an upload session in 1.25 MiB chunks (4 × 320 KiB). Graph documents a
4 MiB practical ceiling for single-request uploads and requires upload-session
chunks to be a multiple of 320 KiB; those constants live in
`packages/onedrive-spike/src/graph/graph-client.ts`. Record the largest file the
firm's account actually needs, and whether the observed behaviour matches.

### Upload interruption

The `upload_interruption` scenario records `interruption.firstChunkBytes`,
`interruption.resumedFromByte`, `interruption.resumedChunkCount`, and
`interruption.contentVerified`. Resumption is driven by the `nextExpectedRanges`
value the provider returns for the session, not by client-side bookkeeping, and
the resumed file is downloaded and checksum-verified.

### Revoked consent and the reconnect procedure

The `revoked_consent` scenario records `revocation.errorCode`,
`revocation.httpStatus`, `revocation.reconnectRequired`, and
`reconnect.succeeded`.

The reconnect procedure that TaxDesk will rely on is:

1. Detect the reconnect-required rejection (`invalid_grant`,
   `interaction_required`, `consent_required`, `login_required`, or
   `invalid_client`) rather than treating it as a transient failure.
2. Mark the connection as needing operator attention. Never silently retry
   forever.
3. Re-run delegated consent for the same application and account, requesting
   only the documented scopes.
4. Replace the stored refresh token atomically, and never log or display any
   token value.

## Outcome and blocking decision

`packages/onedrive-spike/src/domain/spike-evaluation.ts` derives the outcome:

| Outcome | When | Blocking decision |
| --- | --- | --- |
| `passed` | All six required scenarios recorded `passed`. | Not raised. |
| `failed` | Any scenario recorded `failed`. | Raised. Do not start Epic 4 or any production OneDrive adapter work. |
| `incomplete` | A required scenario is missing or `skipped`. | Raised. "Not proven" is not "proven safe". |

The evaluation is covered by
`packages/onedrive-spike/src/domain/spike-evaluation.test.ts`.

## Evidence-file safety

The evidence file is committed to the repository, so it must never contain a
provider token, authorization code, or client secret.
`OnedriveSpikeReportSchema` in `packages/shared/src/onedrive-spike.ts` is strict
and rejects any string that looks like a bearer token, a JWT, an OAuth token
field, or a long opaque value. The harness additionally withholds any
observation that trips that check instead of writing it.

No client secret exists for this application, tokens are held in memory only,
and the synthetic test files are deleted before consent is revoked.

## Troubleshooting

| Symptom | Meaning and action |
| --- | --- |
| `the delegated callback failed with state_mismatch` | The callback did not belong to this run. Close stray browser tabs and start again. |
| `the delegated callback failed with callback_timeout` | Consent was not completed within five minutes. Re-run. |
| `the delegated callback failed with access_denied` | Consent was declined, or the account cannot consent to the app. Use the intended Personal account. |
| `AADSTS50011` in the browser | The registered redirect URI does not match `http://<host>:<port>/oauth/callback` exactly. Fix the app registration or pass matching `--host`/`--port`. |
| `AADSTS65001` / `consent_required` | The app-folder scope was not consented. Grant consent for the test account. |
| `consent` scenario fails on `Files.ReadWrite.AppFolder` | The permission was added as application (app-only) instead of delegated. Fix the app registration. |
| `upload` fails with `quotaLimitReached` | The test account's OneDrive is full. Free space and re-run. |
| `revoked_consent` reports "had not been revoked" | Consent was still active when the refresh was attempted. Revoke at <https://account.live.com/consent/Manage> and re-run. |
| `consent` fails with `403 accessDenied` | Almost always a scope problem: the permission was added as *application* instead of *delegated*, or an older registration was reused. Check `API permissions` and re-consent. Do not add `Files.ReadWrite.All` to work around it. |
| `upload` fails with `404 itemNotFound` on both the attempt and the retry | The app folder cannot be created for this account. Confirm the app is registered for *Personal Microsoft accounts only* and that `Files.ReadWrite.AppFolder` was consented. |
| `offline_access` missing from `grantedScopes` | Expected. Microsoft does not echo it; `consent.refreshTokenIssued: true` is the proof. |
| Port already in use | Pass a different `--port` and register the matching redirect URI. |
| The browser cannot reach the callback | `localhost` may resolve to IPv6 on some machines. Re-run with `--host 127.0.0.1` and register `http://127.0.0.1:<port>/oauth/callback` as the redirect URI. |
