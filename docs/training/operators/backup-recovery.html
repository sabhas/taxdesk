Backup, restore and lockouts

The operator procedures for bad days: restoring the database within four hours, and getting a locked-out administrator back in. None of this has an app screen. It all runs from a trusted operator workstation.

Backup layers

Layer What Checked by
Managed backups and point-in-time recovery (PITR) The database provider's automated backups and write-ahead-log retention ci:backup-check daily, against the operator's posture evidence
Independent export Daily pg_dump, AES-256-GCM encrypted, in R2 under <environment>/, kept 35 days backup-export.yml and ci:backup-verify. Fails if the latest export is missing, failed, older than 30 hours, or kept for less than 30 days.
Documents are not in the database backup

Files live in OneDrive. A database restore brings back document records, not files. Run reconciliation after every restore to flag anything missing.

ops commands

Each prints one JSON line at the end and never prints secrets.

Command Purpose Main flags
pnpm ops:backup-export Encrypted export plus manifest --out --environment --retention-days --storage --key-version
pnpm ops:backup-decrypt Decrypt an export for pg_restore --in --out
pnpm ci:backup-verify Check a manifest (and optionally the artifact digest) --manifest --artifact --max-age-hours --min-retention-days --environment
pnpm ops:recovery-snapshot Record counts, money totals, and integrity checks for a database --out
pnpm ops:restore-verify Compare a restored database with the snapshot and the 4-hour target --expected --incident-start --mfa-key-versions --out
pnpm ops:sample-import Synthetic import CSVs for rehearsals and training --out --clients --seed --service --tax-year --as-of --with-exceptions

Restore procedure (4-hour target)

Start the clock when the decision to restore is made, and record each step's time in the evidence form in docs/guides/backup-and-restore.md.

  1. Declare and freeze. Record the incident start (UTC). Stop writes by deploying the previous build in maintenance, or by removing the Pages route.
  2. Snapshot the source if it still answers: 
    DATABASE_URL=<source> pnpm ops:recovery-snapshot --out source-snapshot.json
    If it does not answer, use the last rehearsal snapshot and note that you did.
  3. Choose the path. Either use PITR in the provider console to restore into a new database, or restore the independent export: 
    pnpm ci:backup-verify --manifest <file>.manifest.json --artifact <file>.dump.enc --max-age-hours 9999
BACKUP_ENCRYPTION_KEY=<from the offline key store> \
  pnpm ops:backup-decrypt --in <file>.dump.enc --out restore.dump
createdb <new database>
pg_restore --no-owner --no-privileges --exit-on-error -d <new database url> restore.dump
    Delete restore.dump once the restore is verified.
  4. Roles and posture. Recreate the least-privilege app role and its grants, then run DATABASE_URL=<new> pnpm ci:db-posture.
  5. Verify. 
    DATABASE_URL=<new> pnpm ops:restore-verify \
  --expected source-snapshot.json --incident-start <UTC from step 1> \
  --mfa-key-versions 1 --out restore-evidence.json
    It checks migrations and checksums, that the firm is bootstrapped, that an MFA administrator exists, MFA key versions, case status against history, invoice paid amounts against payments minus reversals, counts and money totals, and the elapsed time.
  6. Repoint. Update the environment's Hyperdrive config to the new database. Confirm the secrets are unchanged (the MFA, client, and storage keys must be the same as before), then redeploy.
  7. Functional check. Sign in with MFA. Open a client (masked IDs show), a case (status and history), an invoice (balance), and a document (opens). Run pnpm ci:staging-smoke and storage reconciliation.
  8. Reopen and record the total recovery time.

Restore rehearsal (TD-708)

Before go-live, and then quarterly: restore staging's latest export into an isolated database, run steps 4–7 against it, and keep restore-evidence.json and the completed evidence form. It counts only if it finishes within four hours.

Administrator lockout

There is no "forgot password" link and no email. Most problems are fixed inside the app by another administrator. The offline tool is a last resort and needs the environment's DATABASE_URL.

Situation Try first Offline action
A staff member forgot their password An administrator issues Reset link under Users reset-password
A staff member lost their authenticator They sign in with a recovery code, then re-enrol on the Security page disable-mfa
The only administrator forgot their password — reset-password
The only administrator lost the authenticator and the recovery codes — disable-mfa
The only administrator was deactivated — reactivate 
pnpm auth:recover
# asks for the username and action, then asks you to type the username again

# non-interactive form
pnpm auth:recover --non-interactive --username admin --action disable-mfa --confirm admin

Every action revokes all of that user's sessions and writes a user.recovery_* audit event with no actor. Exit codes: 0 done, 1 refused (for example, an unknown user), 2 usage error.

Afterwards:

  1. The user signs in (after disable-mfa they must enrol MFA again) and stores the new recovery codes.
  2. An administrator finds the user.recovery_* event in Audit history and logs the operator, the reason, and the time.
  3. If compromise is suspected, review auth.login_failed events and deactivate accounts as needed.
Prevention is cheaper

Keep at least two administrators. Keep recovery codes in the firm's vault. auth:bootstrap never creates a second "first" administrator; promote an existing user from Users instead.
