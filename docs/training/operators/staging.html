Staging environment

Staging is a full copy of production that only ever holds synthetic data. You use it to demonstrate stories, to run UAT, and to rehearse migrations and restores.

Routine staging deploys are automatic

After CI passes on main, the deploy-staging.yml workflow migrates the database, checks posture, deploys, and smoke-tests. Use the steps below only to provision staging for the first time or to repair it. The detailed runbook is docs/guides/staging-deployment.md.

Current state of staging

  • Staging is provisioned, uses a least-privilege non-owner database role, passes ci:db-posture, and has passed a 15/15 smoke check.
  • The Hyperdrive ID is committed in [env.staging].
  • Still to configure before the Epic 1–7 features work there: the secrets listed under step 6, migrations 0002–0010, a Microsoft app registration, and the backup secrets and R2 bucket.

First-time provisioning

  1. Tools and login. Complete local setup steps 1–2, then run pnpm exec wrangler login and pnpm exec wrangler whoami.
  2. Database. Create a separate managed PostgreSQL database (for example taxdesk_staging) with encrypted automated backups and point-in-time recovery. Create a least-privilege application role that does not own the schema and has no superuser, CREATEDB, or CREATEROLE rights. Test the TLS connection: 
    psql "postgres://<app-role>:<password>@<host>:5432/taxdesk_staging?sslmode=require" \
  -c "select current_database(), current_user;"
  3. Hyperdrive. 
    pnpm exec wrangler hyperdrive create taxdesk-staging \
  --connection-string="postgres://<app-role>:<password>@<host>:5432/taxdesk_staging?sslmode=require"
    Put the returned ID in [[env.staging.hyperdrive]] in packages/api/wrangler.toml, then run pnpm ci:config-posture.
  4. Migrations. 
    DATABASE_URL="postgres://<app-role>:<password>@<host>:5432/taxdesk_staging?sslmode=require" pnpm db:migrate
DATABASE_URL="…same…" pnpm db:migrate:status --check
DATABASE_URL="…same…" pnpm ci:db-posture
    The first migration needs permission to create tables. If it fails with permission denied for schema public, grant the schema permissions or run that first migration as the owner role.
  5. Deploy the API. Run pnpm deploy:api:staging and check https://taxdesk-api-staging.<subdomain>.workers.dev/health.
  6. Secrets and variables for Epics 1–7. 
    for name in MFA_ENCRYPTION_KEY CLIENT_DATA_ENCRYPTION_KEY CLIENT_IDENTIFIER_INDEX_KEY \
            STORAGE_TOKEN_ENCRYPTION_KEY TURNSTILE_SECRET_KEY; do
  pnpm exec wrangler secret put "$name" --config packages/api/wrangler.toml --env staging
done
pnpm exec wrangler secret list --config packages/api/wrangler.toml --env staging
    In [env.staging.vars] set TURNSTILE_SITE_KEY, ONEDRIVE_CLIENT_ID, and APP_PUBLIC_URL (the staging Pages URL), then deploy the API again. See Configuration and secrets.
  7. Pages project (once). 
    pnpm exec wrangler pages project create taxdesk-web-staging --production-branch main
    Staging deploys to the staging preview branch, so the [env.preview] binding points to taxdesk-api-staging. Keep main as the project's production branch.
  8. Deploy the web app. Run pnpm deploy:web:staging. The staging URL looks like https://staging.taxdesk-web-staging.pages.dev.
  9. Same-origin checks. 
    curl -fsS https://<staging-pages-host>/health | jq -e '.environment == "staging"'
curl -fsS https://<staging-pages-host>/api/v1/app-info | jq -e '.name == "TaxDesk API"'
STAGING_WEB_URL=https://<staging-pages-host> pnpm ci:staging-smoke
  10. Bootstrap the firm. Run DATABASE_URL="…staging…" pnpm auth:bootstrap interactively, sign in, and enrol MFA. Store the staging recovery codes in the firm's vault.
  11. Connect OneDrive with a dedicated staging Microsoft account. See OneDrive document storage.
  12. CI wiring. Add the GitHub staging environment secrets and variables, and set branch protection. See CI and delivery.

Health contract

GET /health returns exactly three fields, with Cache-Control: no-store. Anything more is a defect. 

{ "environment": "staging", "releaseVersion": "<commit sha>", "requestId": "…" }

Every API error is a Problem Details JSON body with a requestId. Quote that ID when reporting a problem; it matches the Worker log line and the audit event.

Watching logs

pnpm exec wrangler tail taxdesk-api-staging

Logs are structured JSON with the event name, request ID, and error class only. They never contain secrets, tokens, or document contents.

Making staging ready for UAT

  1. All secrets set, migrations current, health and smoke checks green.
  2. Administrator bootstrapped and storage connected (status Connected).
  3. One test account per role, synthetic data imported. See Build a training environment.
  4. Record the deployed SHA from /health on the UAT results sheet.
Synthetic data only

Staging must never hold a real client's name, CNIC, NTN, or document, not even "just to try something".
