Provisioning production

Follow the same steps as staging, with these differences:

  1. Separate everything. New database, new least-privilege role, new Hyperdrive config (taxdesk-production), new keys, new Turnstile widget, new Microsoft app registration with the production redirect URI, and a firm-owned Microsoft account for OneDrive.
  2. Update wrangler.toml. Replace the production Hyperdrive placeholder and set [env.production.vars]: RELEASE_VERSION, APP_PUBLIC_URL, TURNSTILE_SITE_KEY, ONEDRIVE_CLIENT_ID. Merge this through a normal pull request so CI checks it.
  3. Secrets. Run wrangler secret put … --env production for each Worker secret. Store copies in the offline key store before going further.
  4. Migrate and check posture. 
    DATABASE_URL="<production url, sslmode=require>" pnpm db:migrate
DATABASE_URL="…" pnpm db:migrate:status --check
DATABASE_URL="…" pnpm ci:db-posture
  5. Deploy the exact commit that passed staging. 
    git checkout <approved-sha>
pnpm install --frozen-lockfile
pnpm exec wrangler pages project create taxdesk-web-production --production-branch main   # first time only
pnpm deploy:api:production
pnpm deploy:web:production
  6. Verify. Check /health (it should report production and the approved release version) and /api/v1/app-info on the production host.
  7. Bootstrap and secure. Run pnpm auth:bootstrap interactively. The administrator enrols MFA and stores the recovery codes in the firm's vault. Invite a second administrator straight away, so a single lost phone never needs the offline recovery tool.
  8. Configure the firm. Review Firm settings, connect Document storage, create services and publish workflows.
  9. Production backups. Add a production GitHub environment with the backup secrets (same names as staging) and confirm the first export and posture runs are green.
  10. Import with the same templates and steps you rehearsed (Epic 8 pilot), then reconcile. See Data import.

Rollback

Situation Action
The new release misbehaves but the data is fine Check out the last good SHA and run the two production deploy commands again. Migrations are forward-only, so only roll back code that is compatible with the current schema.
A migration is wrong Write a new compensating migration. Never edit or delete an applied one.
The data is damaged or lost Stop writes, then follow the restore procedure (4-hour target)
Suggested triggers A data-integrity check fails, sign-in is unavailable for 30 minutes, or reconciliation does not match after the production import

Ongoing operations

  • Daily: check the backup export and platform posture workflows. Act on any issue they open.
  • Weekly: look at Document storage health and run reconciliation.
  • Monthly: review users and roles, deactivate leavers, and scan Audit history for auth.login_failed spikes.
  • Quarterly: run a restore rehearsal, and review dependencies and the security review.
  • On staff departure: deactivate the account the same day. This ends their sessions immediately. Also remove their share of the OneDrive app folder.
