Those two decisions make sense for the application architecture, with one important security consideration: your application can have its own authentication and role system, independently of Microsoft sign-in. You can still use Microsoft Graph for OneDrive integration behind the scenes.

I'd revise the plan around these principles:

- One shared Microsoft account is used for the firm's OneDrive storage.
- Staff sign in to the tax application using individual usernames or email addresses and passwords managed by your app.
- An initial administrator account is provisioned securely during setup.
- The administrator creates users, assigns roles, and manages access.
- All client records, tax cases, invoices, and payments live in a shared database, not in OneDrive files.

One distinction worth keeping in mind: Microsoft's allowance for using Office apps on multiple devices does not automatically make OneDrive a multi-user business repository. Your app must handle file access and sharing deliberately, and sharing one Microsoft account also means the activity may not be attributable to a specific staff member at the Microsoft account level. Your application's own audit log should identify each staff member's actions.

## 2. Authentication and user roles

I'd use a custom authentication system with server-managed sessions, rather than implementing authentication tokens entirely in the frontend.

### Initial administrator provisioning

On the first deployment:

1. A one-time setup command or protected bootstrap operation creates the initial administrator.
2. Credentials are supplied securely through deployment configuration or a one-time setup flow.
3. The administrator is required to change the initial password on first login.
4. Bootstrap is permanently disabled once the administrator exists.
5. No default password is hardcoded in the source code.

For passwords, use Argon2id or another well-established password-hashing implementation suitable for the runtime. Never store plaintext passwords.

For sessions, use secure, HTTP-only cookies, CSRF protection where applicable, session expiration, and server-side revocation.

### Recommended roles

Use role-based access control (RBAC), with permissions enforced in the API.

| Role | Typical permissions |
| --- | --- |
| Admin | Manage users, roles, settings, all records and audit logs |
| Partner / Manager | View all clients, assign cases, approve work, review financial reports |
| Tax Consultant | Manage assigned clients, cases, documents and tasks |
| Billing Staff | Manage invoices, payments, receipts and billing reports |
| Read-only | View explicitly permitted records without modifying them |

These should be configurable rather than hardcoded wherever practical. You can start with three roles and add more later.

I'd also distinguish between roles and permissions. For example, `invoice.create`, `invoice.void`, `payment.record`, `client.view` and `user.manage` are permissions. A role is a named collection of permissions. That gives you flexibility without scattering role-name checks throughout the application.

## 3. How OneDrive will work with custom authentication

Your staff should never need Microsoft sign-in to use the tax application. However, OneDrive still needs its own authorisation to access files.

I'd design the integration as follows:

- The administrator connects the firm's OneDrive account once during setup.
- The application uses Microsoft Graph to access the authorised files.
- Microsoft OAuth tokens are stored and protected server-side, never exposed to the React application.
- Staff access documents through your application API, which checks their application permissions before allowing an operation.
- If the Microsoft connection expires or is revoked, the application displays a reconnect prompt to the administrator.

This is a separate integration from your application's username/password authentication.

Important limitation: Microsoft 365 Personal is designed for an individual, even though Office apps can be used across multiple devices. Before relying on one account as a shared business document repository, review Microsoft's account and sharing terms. For a tax firm, a business storage account with centrally managed access may eventually be the safer option.

## 4. Database changes

I'd add or expand these tables to support authentication and permissions:

| Table | Purpose |
| --- | --- |
| `users` | User identity, password hash, active status |
| `roles` | Role definitions |
| `permissions` | Available application permissions |
| `user_roles` | Assigns roles to users |
| `role_permissions` | Maps roles to permissions |
| `sessions` | Active sessions and expiry |
| `audit_logs` | User activity and important record changes |
| `integration_connections` | OneDrive connection metadata |
| `documents` | OneDrive file IDs and associated client/case records |

For `integration_connections`, store encrypted tokens only if the integration requires persistent tokens, and keep the encryption key outside the database in a secret-management facility. Never store raw refresh tokens in ordinary application records or logs.

## 5. Updated implementation priorities

I'd now build in this order:

1. Foundation: React, Hono, Cloudflare Workers, D1, migrations and environment configuration.
2. Authentication: Admin bootstrap, login/logout, password hashing, sessions and account recovery.
3. Authorisation: Roles, permissions, user management and audit logging.
4. Client management: Client profiles, search, tax cases and status history.
5. Billing: Invoices, payment recording, receipts and reconciliation.
6. OneDrive: Account connection, document upload/download and permission checks.
7. Operations: Backups, recovery tests, monitoring and deployment automation.

One further security recommendation: because all three staff members can modify financial records, log who created and changed each invoice, payment, case status and user permission. Never let an administrator's ability to manage users silently erase the financial audit trail.

My final architecture remains React + TypeScript + Hono + Cloudflare Workers + D1, with custom authentication and OneDrive as a document integration. The two items I'd validate before committing to implementation are OneDrive Personal's suitability for your sharing model and the exact authentication/token-storage approach for Microsoft Graph.
