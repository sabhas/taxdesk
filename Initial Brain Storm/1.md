# Comprehensive implementation plan: Tax Firm Management System

Given your requirements, my primary recommendation is React + TypeScript + Cloudflare Workers + D1, with OneDrive used for document storage where practical.

This gives you a custom application for three simultaneous users without maintaining a traditional server. Cloudflare currently offers a free tier with 100,000 Worker requests per day and a D1 allowance of 5 GB total storage, 5 million rows read per day, and 100,000 rows written per day. Those limits are generous for a small firm's ordinary workload, though they are not a guarantee of uninterrupted production service.

## 2. System architecture

I'd keep the application as a modular monolith: one frontend, one API, one database, and a small number of integrations.

Three authorised users

Browser or installed desktop shortcut

React + TypeScript

Forms, dashboards, client records, billing

Cloudflare Worker API

Authentication checks, validation, permissions, business rules

D1

Transactional business records

OneDrive

Documents and PDFs

### How simultaneous editing should work

Imagine two staff members open the same client record.

1. Both load the current record and its version number.
2. The first person saves a change.
3. The second person attempts to save an older version.
4. The API detects the conflict and asks the second user to refresh or merge the change.

For financial records, use database transactions and server-side validation. Never trust totals calculated only in the browser.

For invoices and payments, use immutable payment entries and correction/reversal entries rather than silently overwriting financial history.

## 3. Functional modules

Build these modules in the following order.

A. Client management

Client ID, name, contact details, CNIC/NTN where applicable, client type, assigned staff member, notes, and active/inactive status. Support duplicate detection and global search.

B. Tax cases and filing status

Each case has a service type, tax year, due date, assigned user, workflow status, document checklist, filing reference and completion date. Preserve each year's history.

C. Billing and payments

Configurable service fees, invoices, line items, discounts, partial payments, receipts, outstanding balances, and invoice PDFs. Separate tax-case status from payment status.

D. Document management

Organise files by client and tax year. Store document type, upload date, OneDrive file ID, and verification status. Include a missing-document checklist.

E. Tasks and reminders

Assign work to staff, track due dates, follow up on missing documents and unpaid invoices, and show upcoming filing deadlines.

F. Dashboard and reports

Active clients, open cases, overdue tasks, upcoming deadlines, monthly collections, outstanding fees, and staff workload.

G. Administration and audit

Manage the three users, assign roles, configure services and fees, and track who created or modified important records.

## 4. Database design

Use a relational model rather than a single JSON document. These are the main tables I'd create.

| Table | Key fields |
| --- | --- |
| `users` | `id`, `email`, `role`, `is_active` |
| `clients` | `id`, `client_code`, `name`, `tax_id`, `contact_details` |
| `tax_cases` | `id`, `client_id`, `service_type_id`, `tax_year`, `status`, `due_date`, `version` |
| `case_status_history` | `id`, `case_id`, `old_status`, `new_status`, `changed_by`, `created_at` |
| `service_types` | `id`, `name`, `default_fee`, `is_active` |
| `documents` | `id`, `client_id`, `case_id`, `drive_item_id`, `file_name`, `document_type` |
| `invoices` | `id`, `client_id`, `invoice_number`, `issue_date`, `due_date`, `status` |
| `invoice_items` | `id`, `invoice_id`, `description`, `quantity`, `unit_price` |
| `payments` | `id`, `invoice_id`, `amount`, `paid_at`, `reference`, `recorded_by` |
| `tasks` | `id`, `client_id`, `case_id`, `assigned_to`, `due_date`, `status` |
| `activity_logs` | `id`, `user_id`, `entity_type`, `entity_id`, `action`, `created_at` |

Additional implementation rules:

- Use UUIDs or another stable internal identifier for records.
- Use integer minor currency units for financial calculations where appropriate.
- Enforce foreign keys, unique invoice numbers, and valid status transitions.
- Record timestamps in UTC and display them in the firm's local timezone.
- Keep tax year, filing date, payment date, and invoice date as separate fields.
- Add an optimistic concurrency `version` or `updated_at` check to editable records.

For a Pakistani firm, keep tax service types and deadlines configurable so changes in filing rules do not require a schema redesign.

## 5. OneDrive integration: the part to validate early

This is the biggest integration risk in your current setup.

Microsoft 365 Personal is not a business tenant. A personal OneDrive belongs to an individual account, and sharing it does not automatically give the other two staff members access to all files. Microsoft also documents restrictions on personal OneDrive sharing.

Microsoft Support

+1

I'd implement document storage in two stages:

Stage 1 — Working MVP

- Create a dedicated folder structure in OneDrive.
- Store links or file IDs in the application's `documents` table.
- Open documents through Microsoft-supported sharing or authentication flows.
- Test access using all three users' real accounts.

Stage 2 — Automated Graph integration

- Register the application with the Microsoft identity platform.
- Implement OAuth sign-in and the minimum permissions required.
- Use Microsoft Graph to upload, download, and locate files.
- Handle expired tokens, revoked consent, deleted files, and sharing changes.

Do not store refresh tokens or other secrets in frontend code. A server-side integration must protect tokens and enforce access rules. Microsoft recommends selecting the least-privileged permissions needed for each operation.

If your personal OneDrive sharing model proves too restrictive for the firm's working practices, keep the data model independent of the provider so you can later move document storage to business OneDrive/SharePoint or another controlled repository.

## 6. API design

Keep the frontend thin. The API should enforce permissions, validate inputs, and perform all financial calculations.

A possible endpoint structure:

text

```
/api/auth/me

/api/clients
/api/clients/:id
/api/clients/:id/cases
/api/clients/:id/documents

/api/cases
/api/cases/:id
/api/cases/:id/status-history

/api/invoices
/api/invoices/:id
/api/invoices/:id/payments
/api/payments/:id/reverse

/api/tasks
/api/dashboard/summary
/api/reports/revenue
/api/reports/outstanding-balances

/api/admin/users
/api/admin/services
/api/admin/audit-logs
```

Use pagination for lists, filtering on the server, and consistent error responses. Avoid exposing unrestricted database queries to the client.

For example, an invoice payment operation should execute in a single database transaction:

1. Validate the invoice and payment amount.
2. Insert the payment entry.
3. Recalculate the invoice balance.
4. Update the invoice's payment status.
5. Record an audit event.
6. Commit the transaction.

The operation should be idempotent where retries are possible, so a network retry cannot accidentally record the same payment twice.

## 7. Security and reliability requirements

Tax data needs stronger protection than an ordinary task tracker. I'd make the following part of the initial release, not a later enhancement.

- Authentication: Allow only the three approved user identities. Don't rely on hiding a registration page.
- Authorisation: Enforce role and record access rules on the API, not just in the UI.
- Secrets: Keep Microsoft client secrets, encryption keys and other credentials out of source control and browser bundles.
- Auditability: Log invoice edits, payment entries, status changes, document actions and administrative changes.
- Backups: Export the database regularly to a separate location, test restoration, and keep a defined retention policy.
- Data protection: Use HTTPS, validate inputs, avoid logging tax IDs or document contents, and protect downloadable files.
- Session security: Handle expired sessions and revoked access; use secure cookie practices if your backend uses cookies.
- Operational monitoring: Alert on failed backups, repeated authentication failures, database errors and storage/API limit issues.

Cloudflare D1's free tier has limits, and reaching a quota can make database operations fail. Implement error handling and monitoring rather than assuming every operation will always succeed.

## 8. Development roadmap

I'd deliver the application in small increments, with a usable release at each stage.

### Phase 0 — Validate the foundation

Before feature development

- Confirm the Cloudflare account and current free-tier terms.
- Test D1 migrations, transactions and backup/restore.
- Test Microsoft sign-in for all three accounts.
- Prove that each user can access the required shared OneDrive files.
- Establish the permission model and data retention policy.

Exit criterion: all three users can access a prototype and the same test records without conflicts.

### Phase 1 — Core MVP

- Authentication and user roles.
- Client CRUD, search and duplicate detection.
- Tax case creation, status tracking and deadlines.
- Dashboard and basic filters.
- Audit log and initial database backup process.

Exit criterion: the firm can manage clients and cases without spreadsheets.

### Phase 2 — Billing

- Invoices and invoice items.
- Partial payments, receipts and balances.
- PDF generation.
- Revenue and outstanding-payment reports.
- Immutable payment history and correction workflows.

Exit criterion: financial totals reconcile against sample invoices and payment scenarios.

### Phase 3 — Documents and workflow

- OneDrive file integration.
- Document checklists and verification.
- Staff assignments and reminders.
- Deadline calendar and activity history.
- Secure exports and restore testing.

Exit criterion: a tax case can move from onboarding through filing and completion.

### Phase 4 — Pilot and production

- Test simultaneous edits and duplicate payment submissions.
- Test all role permissions.
- Verify backup recovery and incident procedures.
- Import a small, cleaned sample of existing records.
- Train staff and document the operating procedures.

Exit criterion: the three users complete realistic workflows without data conflicts or unauthorised access.

For a senior TypeScript developer, a focused MVP could be achievable in a few weeks, depending on how much billing, document integration, and migration work is needed. The OneDrive identity and sharing proof-of-concept is the part I'd tackle first because it could change the architecture.

## 11. Important trade-off: OneDrive Personal versus business storage

I would not make your application's core database depend on OneDrive. Keep it in D1 and use OneDrive for the documents.

However, before using personal OneDrive as the firm's shared document repository, verify the three users' access model, sharing restrictions, and account recovery arrangements. A personal account is not equivalent to a centrally managed business tenant. If your firm grows or needs stronger administrative control, a business Microsoft 365 plan may be worth considering later.

Also, Cloudflare hosting and OneDrive are two separate services: your application can use both, but Microsoft 365 Personal does not itself provide a hosted backend or shared relational database.

## 12. Final recommendation

I'd proceed with this stack:

Custom web interface

Hono + Cloudflare Workers

Serverless API and business logic

Cloudflare D1

Shared SQL database

Microsoft Graph + OneDrive

Client document storage, subject to access validation

Zod + Drizzle + Vitest + Playwright

Validation, database access, and testing

I'd defer Tauri desktop packaging until the web app is stable. A responsive web application can be installed as a shortcut or progressive web app, while keeping a single codebase and deployment pipeline.

The most important first milestone is not the dashboard: it is proving three-user authentication, shared OneDrive document access, reliable concurrent database updates, and recoverable backups. Once those work, the rest of the application is a conventional TypeScript business system.
